# 함께 고르기 (2단계) Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 방을 만들고 6자리 코드로 참여해, 내장 메뉴 중 후보를 올리고 투표하면 실시간으로 반영되고, 방장이 마감하면 1등 메뉴로 결정되는 기능을 만든다.

**Architecture:** Supabase Postgres에 테이블 4개 + RLS + security definer RPC 3개를 마이그레이션으로 올린다. 앱은 `features/room/`에 API·Realtime 훅·집계 순수 함수를 두고, `app/room/` 화면 2개에서 쓴다. Realtime은 "구독 → 스냅샷 → 이벤트마다 다시 불러오기"만 한다.

**Tech Stack:** Expo SDK 58 + Expo Router, TypeScript, Zustand(persist), @supabase/supabase-js, Jest(jest-expo), Supabase CLI 3.3.0(`npx -y supabase@3.3.0`)

**Spec:** `docs/superpowers/specs/2026-11-24-together-design.md` (실행자는 이 문서도 함께 읽는다)

## Global Constraints

- 후보는 내장 메뉴 80개(`src/data/menus.json`)의 ID만. 자유 입력 없음.
- 방 코드: `^[0-9]{6}$`, 전체 방에서 유일. 닉네임: trim 후 1~20자. `menu_id`: `^m[0-9]{2,3}$`.
- 쓰기 권한: 방 생성·참여·마감은 RPC(`create_room`, `join_room`, `close_room`)로만. 후보 추가와 투표는 RLS 정책으로 허용한 insert/upsert.
- 1등 결정은 서버(`close_room`)만 한다. 득표 내림차순 → 동점이면 `created_at`, `id` 오름차순. 멱등.
- `anon` 역할에는 아무 권한도 주지 않는다. 정책·RPC 실행 권한은 `authenticated`만.
- Realtime: 먼저 구독하고(SUBSCRIBED 시점) 스냅샷을 불러온다. 이벤트마다 다시 불러오고, 화면을 떠나면 `supabase.removeChannel`.
- `.env`가 없으면(`supabase === null`) 홈의 "함께 고르기"는 비활성, 1단계는 그대로.
- 패키지 추가 금지(필요한 건 모두 설치돼 있음). UI 문구는 한국어, 기존 `src/components/ui.tsx` 컴포넌트와 색상 사용.
- 원격 DB(`xilrjqeabpjqqhdrwefn`)에 바로 적용한다. CLI가 production 변경에 `--yes`를 요구한다.

## Review Focus

1. 같은 메뉴를 두 사람이 동시에 후보로 추가 → 하나만 남고, 실패한 쪽은 에러 없이 다시 불러온 목록을 본다. (Task 3 `toRoomError` 테스트: `23505` → `duplicate`)
2. 마감 직후에 도착한 투표·후보 추가 → 서버가 거부하고, 화면은 결과 화면으로 바뀐다. (Task 1 DB 확인: 마감 후 투표 거부)
3. 투표자가 다른 방의 `candidate_id`로 upsert → 복합 FK가 거부한다. (Task 1 DB 확인)
4. 닉네임을 저장해 둔 채 링크로 방에 다시 들어오기 → 입력 없이 바로 방이 보이고 멤버가 늘지 않는다. (Task 1 DB 확인: `join_room` 두 번 → 멤버 1명)
5. 공백만 있는 닉네임, 21자 닉네임 → `bad_nickname` 오류, 화면에 안내. (Task 1 DB 확인 + Task 3 `toRoomError`)

- [ ] **Step 2: SQL 작성.** 스펙의 "DB" 절 그대로. 정할 것만 적는다:
  - 테이블·제약은 스펙 표 그대로(`unique (room_id, id)` + votes의 복합 FK 포함). 4개 테이블 모두 `enable row level security`.
  - `is_member(p_room uuid)`, `room_open(p_room uuid)`: `language sql stable security definer set search_path = public`.
  - 정책은 스펙의 권한 표 그대로, `to authenticated`. votes는 insert 정책 + update 정책(using/with check 같은 조건).
  - RPC 3개: `language plpgsql security definer set search_path = public`. 각각 `revoke execute ... from public, anon; grant execute ... to authenticated;`. `is_member`, `room_open`도 같은 revoke/grant.
  - `create_room`: 코드는 `lpad((floor(random()*1000000))::int::text, 6, '0')`, unique 위반이면 반복(최대 10번 후 예외).
  - `join_room`: `insert into members ... on conflict (room_id, user_id) do update set nickname = excluded.nickname`.
  - `close_room`의 1등 선택(방 행은 `select ... for update`로 먼저 잠금):
    ```sql
    select c.menu_id into v_winner
    from candidates c left join votes v on v.candidate_id = c.id and v.room_id = c.room_id
    where c.room_id = p_room
    group by c.id
    order by count(v.user_id) desc, c.created_at asc, c.id asc
    limit 1;
    ```
  - 맨 끝: `alter publication supabase_realtime add table rooms, members, candidates, votes;`
